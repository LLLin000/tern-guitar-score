# Generative UI DSL prior art: what gscore should and should not borrow

Status: research only. No code changes, no tests.
Method: first-party sources only (official docs, spec pages, official GitHub org). Every claim below cites its source next to it. Anything not directly observed is marked **[INFERENCE]** or **[NOT VERIFIED]**.

Context: the question is whether `gscore.lesson` should move from fixed explanation / chord-diagram / quiz activities toward an Agent-designed generative visual canvas. The current implementation works end-to-end (Tern + OMP path, closed lesson payload, deterministic music facts via Tonal + curated chords-db + SVGuitar sanitized static SVG, Tern-native buttons, immutable revisions, persisted attempts) **[ASSIGNMENT-CONTEXT]**. This note compares seven prior-art families and ends with a recommendation.

## 1. A2UI (Google / current A2UI project): a protocol, not a component library

- What it is **[VERIFIED]**: "A Specification for a JSON-Based, Streaming UI Protocol", v1.0 status Candidate (v0.9.1 is the current production version), "a unidirectional stream of JSON messages from an agent to a renderer" — https://a2ui.org/specification/v1.0-a2ui/
- Message / stream model **[VERIFIED]**: four agent-to-renderer message types — `createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface` — plus end-of-turn signaled by the transport layer; v1.0 adds typed bidirectional function messages (`callRendererFunction`, `callAgentFunction`, `rendererFunctionResponse`, `agentFunctionResponse`); v1.0 also allows initial components + data model embedded in `createSurface` — https://a2ui.org/specification/v1.0-a2ui/
- Transport decoupling **[VERIFIED]**: transport-agnostic by design (reliable ordered delivery, framing, metadata, optional return channel); bindings listed include AG-UI, A2A, MCP, plus SSE/JSON-RPC, WebSockets, REST — https://a2ui.org/specification/v1.0-a2ui/
- Component model **[VERIFIED]**: flat adjacency-list model — components are a flat list with ID references, not nested JSON; static children as ID arrays, dynamic children as `{ path, componentId }` templates; updates are ID-based add/update/remove-by-parent-edit — https://a2ui.org/concepts/components/
- Data model separation **[VERIFIED]**: UI structure (components) is separate from application state (per-surface JSON data model); props take literals or JSON-Pointer (RFC 6901) bindings; `updateDataModel` patches `/path` with a value (`null` deletes); input components bind bidirectionally (TextField, CheckBox, ChoicePicker) — https://a2ui.org/concepts/data-binding/
- Catalog ownership **[VERIFIED]**: every surface is driven by a catalog — a JSON Schema file of components, functions, themes; the Basic Catalog is just a pre-built sparse starter; production apps define their own catalog mirroring their design system; the envelope schema is catalog-agnostic (`catalog.json` placeholder mapped to the basic catalog or the app's own) — https://a2ui.org/concepts/catalogs/ and https://a2ui.org/specification/v1.0-a2ui/
- Validation **[VERIFIED, with one gap]**: all agent-sent JSON is validated against the chosen catalog; catalog strategy calls for two-phase validation (agent pre-send + client-side revalidation, failures reported back to the agent) — https://a2ui.org/concepts/catalogs/. A dedicated validation concept page was requested but returned HTTP 404 (**[NOT VERIFIED]** as a standalone page); the validator-compliance rules that could be verified live in the spec: child-reference fields MUST use the `ComponentId` / `ChildList` schema refs (not raw strings) so validators can check that referenced components exist — https://a2ui.org/specification/v1.0-a2ui/
- Actions **[VERIFIED]**: user interaction travels renderer→agent as `action(name, ...)` events (e.g. button `action: { event: { name: "ok" } }`); v1.0 function calls are "verified against runtime catalog definitions" — https://a2ui.org/concepts/components/ and https://a2ui.org/specification/v1.0-a2ui/
- What this suggests / does not suggest for gscore: the suggestive part is the **pattern** (frontend-owned catalog + envelope validation + structure/data split + ID-based streaming updates), not any A2UI component. A2UI validates **shape conformance to a UI catalog**; it says nothing about whether a chord voicing is musically correct. Adopting A2UI semantics would not remove the need for gscore's deterministic theory layer **[INFERENCE]**.

## 2. CopilotKit Generative UI: agent chooses, frontend owns the catalog

- Spectrum framing **[VERIFIED]**: six primitives on a controlled→declarative→open-ended spectrum — Components-as-Tools / Tool-Call Rendering / State Rendering / Reasoning (controlled), A2UI Dynamic + Fixed Schema (declarative: "agent emits a structured spec; the frontend composes from a catalog you registered. Creativity inside a guardrail"), MCP Apps in a sandboxed iframe (open-ended) — https://docs.copilotkit.ai/concepts/generative-ui-overview
- Controlled primitive **[VERIFIED]**: `useComponent({ name, description, parameters, render })` registers a React component as a frontend tool; the agent calls it by verb-like name (`render_bar_chart`) and CopilotKit renders it inline with typed props; the component itself is ordinary React and "doesn't know anything about CopilotKit" — https://docs.copilotkit.ai/generative-ui/tool-based
- Declarative primitive — catalog **[VERIFIED]**: the catalog is declared once at module level with `createGenerativeUI({ id, components, ... })` (versioned id e.g. `acme/shop@1`); each entry holds the React component, a description the agent reads, a `props` schema (Zod/ArkType/Valibot via Standard Schema, must validate synchronously), and `slots` for children; `extends` merges catalogs, `omit` drops components, `overrides` swaps a renderer while keeping props — https://docs.copilotkit.ai/generative-ui/components/catalogs
- Standard catalog **[VERIFIED]**: `standardUI` ships 69 ready-made components (layout, text, inputs, data incl. `Chart`/`Map`/`Table`, media incl. `Svg`/`HtmlView`, feedback/overlay, composites); the 18 A2UI 1.0 basic-catalog components are included under A2UI names/props; every input validates (`checks` + `ValidationResult` codes); inputs keep user-typed values against later agent overwrites — https://docs.copilotkit.ai/generative-ui/components/standard-catalog
- State and actions **[VERIFIED]**: app state fills props via `bind` + `useGenerativeUIState` (agent never sets or sees bound props); component events run app code via `useGenerativeUIFunction` (name-matched, `allowedCallers` defaults to renderer-only); unmatched events become user-visible messages to the agent carrying a structured A2UI 1.0 `action` payload in metadata; `writable` props give inputs setters whose user edits the agent cannot overwrite; browser-computed values (`@call` incl. CopilotKit's `calc`/`series`) recompute without an agent round trip — https://docs.copilotkit.ai/generative-ui/components/state-and-actions
- Export **[VERIFIED]**: `exportA2UICatalog(ui)` writes the UI as an A2UI 1.0 catalog definition for validators, other renderers, or prompt builders — https://docs.copilotkit.ai/generative-ui/components/catalogs
- What this suggests / does not suggest for gscore: the ownership answer is explicit — **the frontend owns the render catalog and all behavior; the agent only picks which registered component to show and what data to pass**. That maps directly onto gscore's current shape (closed activity set, frontend-owned SVG mapping). What it does not give gscore: CopilotKit components are React, and its `standardUI` has no music-theory components — an agent composing `Chart`/`Svg` from that catalog cannot produce a trustworthy fretboard, and nothing in the catalog layer checks pitch content **[INFERENCE]**.

## 3. Vega-Lite: a semantic visualization grammar with renderer-owned layout

- What it is **[VERIFIED]**: "a high-level grammar for interactive graphics … a concise JSON syntax" compiled by its compiler into lower-level Vega specs and rendered with Vega — https://vega.github.io/vega-lite/docs/
- Spec shape **[VERIFIED]**: top-level `$schema` (+ `background`/`padding`/`autosize`/`config`) with single-view specs built from `data` + `mark` (bar/circle/line/point/text/…) + `encoding` (channel→field mapping over x/y/color/size/shape/text/tooltip/…); composition via `layer`/`facet`/`concat`/`repeat` operators — https://vega.github.io/vega-lite/docs/spec.html and https://vega.github.io/vega-lite/docs/encoding.html
- Renderer-owned layout **[VERIFIED]**: "by simply providing the mark type and the encoding mapping, Vega-Lite automatically produces other visualization components including axes, legends, and scales" from rule-based defaults, overridable explicitly — https://vega.github.io/vega-lite/docs/spec.html
- What this suggests / does not suggest for gscore: the suggestive part is the **grammar→compiler→renderer** split (author declares *what*, renderer owns *how it lays out*), which is exactly the shape gscore already uses (`music_context` → SVG strings via SVGuitar). What it does not suggest: Vega-Lite is a **chart grammar** (statistical marks + encodings + transforms), not a general education canvas — it has no notion of lesson activities, quizzing, attempts, or music-domain facts, so citing it as precedent for agent-designed lesson canvases would be a category error **[INFERENCE]**.

## 4. Excalidraw / tldraw: low-level editable scene JSON with versioning — not fact validation

- Excalidraw file format **[VERIFIED]**: plaintext JSON `.excalidraw` with `type: "excalidraw"`, numeric schema `version`, `source`, `elements[]`, `appState`, `files` (image data keyed by fileId); each element carries `id` plus direct geometry (`x`, `y`, `width`, `height`); every normalized element has `created: number | null` (epoch ms, preserved across restore/edit/undo, renewed on duplicate/paste); clipboard variant uses `type: "excalidraw/clipboard"` — https://docs.excalidraw.com/docs/codebase/json-schema
- tldraw store **[VERIFIED]**: the store is a reactive database holding all records; every record is JSON with `id` + `typeName` (ids branded with type prefixes); record scopes are `document` (persisted + synced), `session` (local), `presence` (synced, not saved); writes go through validated store APIs (`put`/`update`/`remove`) with undo/redo, listeners, and snapshots (`getSnapshot`/`loadSnapshot`, document vs session split) — https://tldraw.dev/sdk-features/store and https://tldraw.dev/docs/persistence
- tldraw schema / migrations **[VERIFIED]**: `StoreSchema` is the central authority for validation + evolution (`getMigrationsSince`, `migratePersistedRecord` up/down, `migrateStoreSnapshot`, `serialize`); a `Migration` targets `record` (with optional filter), `store`, or `storage` scope, each with `up` and optional `down` plus dependencies; custom record types (own validators, scopes, migration sequences) participate in the same regime — https://tldraw.dev/reference/store/StoreSchema and https://tldraw.dev/reference/store/Migration
- What this suggests / does not suggest for gscore: the suggestive part is **versioned scene persistence** (schema-stamped snapshots + up/down migrations), which maps onto gscore's immutable lesson revisions and persisted attempts — payload versioning is the right borrowing. What it does not give: element coordinates, IDs, and migrations validate **shape/schema evolution**, never domain truth — a migrated scene with a wrong chord is still a wrong chord. Static scene JSON does not automatically validate music facts **[INFERENCE]**.

## 5. Vercel `json-render`: catalog (vocabulary) vs registry (implementation)

- What it is **[VERIFIED]**: a "Generative UI framework: AI generates interfaces from natural language prompts, constrained to components you define" — https://github.com/vercel-labs/json-render/blob/main/README.md
- Catalog vs schema **[VERIFIED]**: "The schema is the grammar; the catalog is the vocabulary" — the catalog lists components (Zod `props` schema, optional `slots`, `description` the AI reads), `actions`, and functions, built with `defineCatalog(schema, {...})` where the schema comes from the platform package — https://json-render.dev/docs/catalog and https://json-render.dev/docs/schemas
- Spec shape **[VERIFIED]**: the built-in React schema is a flat `root` + `elements` map; each element has `type`/`props`/`children` plus optional `slots`, `visible`, `repeat`, `watch`; props may carry `$state` JSON-Pointer (RFC 6901) expressions, `$bindState`/`$bindItem` two-way bindings, `$cond`/`$template`/`$computed` dynamics — https://json-render.dev/docs/specs and https://json-render.dev/docs/data-binding
- Rendering and ownership **[VERIFIED]**: `defineRegistry` maps each catalog entry to a platform implementation; components receive resolved props plus `emit`/`on` event handles and `bindings` write-back paths; actions are declared by name in the catalog and implemented app-side as `(params, setState, state)` handlers — "Instead of AI generating arbitrary code, it declares _intent_ by name" — https://json-render.dev/docs/registry
- AI prompting and streaming **[VERIFIED]**: `catalog.prompt()` generates the system prompt from the catalog; progressive rendering via `SpecStream`/`useUIStream`; `validateSpec` checks structural issues — https://json-render.dev/docs/catalog and https://json-render.dev/docs/specs
- Versioning **[NOT VERIFIED]**: no catalog-version field was observed in the docs pages read — unlike CopilotKit's versioned `acme/shop@1` catalog ids, json-render has no documented catalog-versioning story in the sources consulted.
- What this suggests / does not suggest for gscore: the closest implementation-shaped precedent for the proposed `gscore.scene.v1` — catalog/registry split, flat ID map, JSON-Pointer state separation, name-declared app-owned actions all mirror the existing recommendation. What it does not give: still no domain-fact layer — Zod validates prop shape only, so a well-typed spec naming a wrong chord is still a wrong chord; its standard/shadcn component sets are generic UI, not music vocabulary, and the multi-renderer story (email/PDF/video/3D) is out of scope **[INFERENCE]**.

## 6. MCP Apps (SEP-1865): protocol-hosted UI — not an agent-authored DSL

- What it is **[VERIFIED]**: extension `io.modelcontextprotocol/ui`, Status Stable (2026-01-26): "enables servers to deliver interactive user interfaces to hosts" — https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx and https://github.com/modelcontextprotocol/ext-apps/blob/main/docs/overview.md
- DSL boundary **[VERIFIED]**: there is no agent-composed component DSL here — the **server** authors full HTML templates, declared upfront as `ui://` resources (`mimeType` MUST be `text/html;profile=mcp-app`, content MUST be a valid HTML5 document returned via `resources/read`); tools link to their UI via `_meta.ui.resourceUri` — https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx (UI Resource Format) and https://github.com/modelcontextprotocol/ext-apps/blob/main/docs/overview.md (Tool-UI Linkage)
- Ownership **[VERIFIED]**: the **host** owns rendering, sandboxing, and security (sandboxed iframe, restrictive-default CSP, host has final say on display modes/permissions); view↔host talk MCP JSON-RPC over `postMessage` (`tools/call`, `resources/read` from the view; `ui/message`, `ui/update-model-context`, `ui/open-link`); tool results split `content` (model context) from `structuredContent` (UI data); app-only tools (`visibility: ["app"]`) exist for UI-only interactions the model never sees — https://github.com/modelcontextprotocol/ext-apps/blob/main/docs/overview.md
- Degradation **[VERIFIED]**: progressive enhancement — "UI is a progressive enhancement, not a requirement… hosts that don't support UI get text"; capability negotiation between client and server — https://github.com/modelcontextprotocol/ext-apps/blob/main/docs/overview.md. No data-migration story was observed (**[NOT VERIFIED]** as versioning).
- Bridge note **[VERIFIED]**: Vercel's `@json-render/mcp` package serves catalog-constrained json-render specs as MCP Apps (bundled HTML UI resource + tool registration), showing the two compose: constrained spec inside protocol-hosted iframe — https://github.com/vercel-labs/json-render/blob/main/packages/mcp/README.md
- What this suggests / does not suggest for gscore: MCP Apps answers "how does a server ship interactive UI inside a host", not "what JSON may the agent emit" — the opposite direction from gscore's need. Borrow only the containment discipline (predeclared templates, auditable host bridge, text fallback); do NOT borrow sandboxed arbitrary HTML as lesson composition — it would bypass deterministic music validation and Tern-native actions **[INFERENCE]**.

## 7. Mermaid: text-authored diagram DSL with renderer-owned layout (contrast only)

- What it is **[VERIFIED]**: "a JavaScript based diagramming and charting tool that renders Markdown-inspired text definitions" — https://mermaid.js.org/intro/
- DSL boundary **[VERIFIED]**: every diagram begins with a diagram-type declaration followed by definitions; the renderer owns layout (ELK is the default for supported types; Dagre can be selected, and the tiny build falls back to Dagre) and look (neo/hand-drawn/classic, selectable via frontmatter or `initialize()`); per-diagram config via YAML frontmatter or `%%{ }%%` directives — https://mermaid.js.org/intro/syntax-reference.html
- Failure modes **[VERIFIED]**: "Unknown words and misspellings will break a diagram, while parameters silently fail"; reserved words (e.g. `end` in flowcharts) must be quoted — https://mermaid.js.org/intro/syntax-reference.html
- What this suggests / does not suggest for gscore: the same grammar→renderer split as Vega-Lite but for node-link diagrams rather than statistical charts — conceivably the shape of a progression-relationship view. But a syntactically valid diagram with wrong chord labels is still wrong, and a parse-sensitive text DSL with silent-failure modes is the wrong authoring posture for agent-emitted lesson content: the agent should emit typed semantic nodes, not text the renderer may silently misread **[INFERENCE]**. Mermaid is a contrast, not a proposed lesson DSL.

## 9. Recommendation

**Pivot the product direction, not to an unbounded canvas.** The long-term goal should be Agent-selected visual composition. Keep the current `gscore.lesson` host, deterministic music validation, SVG generation, immutable revisions, and persisted attempts as the safety baseline; the present activity types are proven semantic building blocks, not a prewritten course or the final ceiling.

- Add `gscore.scene.v1` as a composition layer inside a new explicit `gscore.lesson.v2`; do not add it to the closed v1 activity set. The current v1 validator rejects unsupported activity types, so keep existing v1 revisions and readers unchanged. The Agent chooses semantic nodes, ordering, comparisons, emphasis, and relationships; the renderer owns layout and pixels.
- Borrow A2UI/CopilotKit/json-render's frontend-owned catalog, typed props/IDs, validation, state, and native action mapping. This permits novel compositions from registered nodes without permitting arbitrary HTML, CSS, JavaScript, or untrusted SVG. json-render adds one concrete vocabulary-vs-implementation phrasing (`defineCatalog` vs `defineRegistry`) but changes nothing about the recommendation — prefer CopilotKit's versioned catalog ids over json-render where versioning matters.
- Borrow Vega-Lite's spec-to-renderer split for chart-like timelines/voice-motion views only; it is not a general Lesson DSL. Mermaid is the parallel cautionary contrast for relationship diagrams: same grammar→renderer shape, but text-DSL fragility (breakage on misspellings, silent param failure) is the wrong authoring posture for agent output — emit typed semantic nodes instead.
- Borrow tldraw/Excalidraw's versioned snapshots and migration discipline, not free coordinates or a human-oriented editing model. Publish a new full revision after a follow-up; defer partial patches and arbitrary primitives until a real lesson requires them.
- Keep MCP Apps out of the composition layer: borrow only its containment posture (predeclared templates, auditable host bridge, text fallback). Server-authored sandboxed HTML is the opposite of agent-composed semantic nodes and would bypass deterministic music validation.
- Keep musical values derived from `gscore_music_query`/the renderer. In particular, “C/E → F is more natural” needs concrete voicings and a declared comparison criterion; it is not a universal fact of the chord symbols alone.
